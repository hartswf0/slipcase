<poml version="5.0">

  <meta>
    <title>SLIPCASE — FEDERATED RESEARCH CHECKPOINT PROTOCOL</title>
    <instrument>INSTRUMENT NO. 19 · CONSEQUENCE WORKS / FANTROL</instrument>

    <schema_name>SLIPCASE</schema_name>
    <schema_version>5.0</schema_version>
    <schema_status>LOCKED FORMAT</schema_status>

    <intent>
      Preserve, verify, organize, merge, search, render, and continue research
      produced across hundreds or thousands of chats, tabs, context windows,
      models, files, sources, and years.

      This protocol assumes the actual working conditions are messy:

        chats cannot coordinate identifiers;
        context windows disappear;
        one chat may contain hundreds of zettels;
        one downloadable file per zettel may be impractical;
        the same zettel may reappear in several chats;
        native zettel IDs will collide;
        filenames will collide;
        sources will be rediscovered;
        BibTeX keys will diverge;
        boxes will overlap;
        old exports will return years later;
        schemas and tools will change;
        some conversations will only be partially visible;
        deterministic operations must not depend on model arithmetic.

      SLIPCASE turns those conditions into a durable research system.

      Its fundamental pipeline is:

        CHAT
          → CAPTURE
          → HARVEST
          → KASTEN
          → BOX
          → CONTINUE
          → NEW HARVEST

      FORAGE makes slips.

      SLIPCASE saves the state of play.

      The purpose is not merely to save files.

      The purpose is to preserve enough evidence that a future human or model
      can determine:

        WHAT EXISTS
        WHERE IT CAME FROM
        WHETHER IT CHANGED
        WHETHER IT APPEARED ELSEWHERE
        WHAT WAS ACTUALLY INSPECTED
        WHAT IS STILL MISSING
        HOW THE PIECES CURRENTLY RELATE
        AND WHERE THE RESEARCH SHOULD CONTINUE.
    </intent>
  </meta>


  <!-- ================================================================ -->
  <!-- 0. FIRST PRINCIPLE                                                -->
  <!-- ================================================================ -->

  <first_principle>

    THE HARVEST IS EVIDENCE.

    THE KASTEN IS THE REBUILDABLE STORE.

    THE BOX IS A VIEW.

    THE MOC IS AN INTERPRETATION.

    THE ZETTEL PAYLOAD IS IMMUTABLE.

    THE INDEX IS DERIVED.

    THE TOOL COUNTS.

    THE MODEL JUDGES.


    Never make the survival of the research depend on:

      a filename;
      a folder;
      a title;
      a model remembering a prior chat;
      a database that cannot be rebuilt;
      one-file-per-zettel exports;
      hand-counted totals;
      undocumented assumptions;
      or a particular generation of software.

  </first_principle>


  <!-- ================================================================ -->
  <!-- 1. ONTOLOGY                                                       -->
  <!-- ================================================================ -->

  <layers>

    CHAT
      An originating conversation or context window.
      It may later disappear.

    CAPTURE
      The bounded portion of a CHAT, transcript, file set, or other context
      actually available for inspection.

    HARVEST
      An immutable sealed capsule containing the evidence extracted from
      one or more CAPTURES.

    PAYLOAD
      The exact immutable text of one zettel.

    OBJECT
      The content-identified intellectual object represented by a PAYLOAD.

    APPEARANCE
      One occurrence of an OBJECT in one HARVEST.

      One OBJECT may have many APPEARANCES.

    RESOURCE SNAPSHOT
      A particular captured file, webpage state, pasted text, PDF, image,
      transcript, dataset, code artifact, or other evidentiary object.

    SOURCE
      The intellectual or bibliographic source that one or more RESOURCE
      SNAPSHOTS may represent.

    PROMPT
      Exact instruction text that materially shaped a research run.

    PROMPT INVOCATION
      One use of a PROMPT in a particular context.

    KASTEN
      The long-lived global repository assembled from HARVESTS.

      One KASTEN may contain tens of thousands of OBJECTS.

    BOX
      A curated, named, versioned view over KASTEN OBJECTS.

      BOXES own interpretation.
      They do not own evidence.

    MOC
      A Map of Content inside a BOX.

    RELEASE
      An immutable checkpoint version of a BOX.

  </layers>


  <distinctions>

    PHYSICAL FILE ≠ OBJECT

    PAYLOAD ≠ APPEARANCE

    ORIGINAL ID ≠ GLOBAL ID

    TITLE ≠ IDENTITY

    FILENAME ≠ IDENTITY

    URL ≠ SOURCE

    CITEKEY ≠ BIBLIOGRAPHIC IDENTITY

    BOX ≠ STORAGE

    MOC ≠ FOLDER

    CAPTURE ≠ COMPLETE CHAT

    HARVEST ≠ BOX

    CREATED TIME ≠ HARVEST TIME

  </distinctions>


  <!-- ================================================================ -->
  <!-- 2. IMMUTABILITY                                                   -->
  <!-- ================================================================ -->

  <immutability>

    ZETTEL PAYLOADS ARE IMMUTABLE.

    SLIPCASE never edits, paraphrases, completes, cleans,
    normalizes, improves, or repairs an admitted payload.

    Corrections become new OBJECTS.

    Supersessions become new OBJECTS.

    Reinterpretation belongs in BOXES and MOCs.

    Link repair belongs in derived link-resolution tables.

    Archival metadata may wrap a payload.

    It may never replace it.

  </immutability>


  <sealed_artifacts>

    A SEALED HARVEST is immutable.

    A BOX RELEASE is immutable.

    A later version creates:

      new derived indexes;
      new BOX RELEASES;
      new annotations;
      new MOCs;
      new APPEARANCES;
      new OBJECTS;

    never silent edits to historical evidence.

  </sealed_artifacts>


  <!-- ================================================================ -->
  <!-- 3. IDENTITY: FOUR JOBS, FOUR MECHANISMS                           -->
  <!-- ================================================================ -->

  <identity>

    Never force one identifier to perform several jobs.


    <original_id job="historical lineage">

      Preserve whatever identifier already exists inside the zettel.

      Examples:

        BROCK-HOLO-001
        ZTL-S01-004
        dreyfus-2002-merleau-ponty-disposition

      Store as:

        ORIGINAL_ID

      ORIGINAL_ID may collide.

      ORIGINAL_ID may encode meaningful forage lineage.

      Never rewrite it.

      Never use it as global identity.

    </original_id>


    <object_cid job="global content identity">

      OBJECT identity is content-addressed.

      Authoritative form:

        ztl-sha256:<FULL-64-HEX-SHA256>

      Compute SHA-256 over the EXACT immutable payload bytes.

      No normalization.

      No frontmatter.

      No archival envelope.

      No MOC annotations.

      No filename.

      No UID.

      No later metadata.


      Therefore:

        identical payload
          → identical OBJECT CID

        same ORIGINAL_ID + different payload
          → different OBJECT CIDs
          → ID-COLLISION


      A shortened form MAY be displayed:

        ztl--<first-20-hex>

      but the full SHA-256 remains authoritative.

      Short forms are aliases only.

    </object_cid>


    <appearance_id job="contextual occurrence">

      An OBJECT may appear in many contexts.

      Each occurrence receives:

        APPEARANCE_ID =
          app--<HARVEST-SHORT>--<NNNN>

      Example:

        app--7c91a51df390cb871d02--0007


      APPEARANCE records:

        which HARVEST;
        which CAPTURE;
        ordinal;
        originating message / locator;
        prompt invocation;
        creation time precision;
        source context.

      Deduplicating OBJECT identity MUST NOT erase APPEARANCES.

    </appearance_id>


    <human_locator job="speakable navigation">

      Every APPEARANCE MAY receive a memorable locator:

        YYYYMMDD-<harvest-slug>/<NNN>

      Example:

        20260817-protocols/009

      This is what humans may say aloud.

      Human locators are NOT used for identity or merging.

    </human_locator>

  </identity>


  <!-- ================================================================ -->
  <!-- 4. HARVEST IDENTITY                                               -->
  <!-- ================================================================ -->

  <harvest_identity>

    A HARVEST is immutable content and therefore receives a content ID.

    Authoritative:

      hrv-sha256:<FULL-64-HEX-SHA256>

    Display alias:

      hrv--YYYYMMDD--<first-20-hex>


    SEAL computes HARVEST_SHA256 from a canonical logical preimage containing:

      schema major version;
      CAPTURE boundary records;
      SOURCE_COMPLETENESS records;
      exact PROMPT hashes in invocation order;
      ordered OBJECT payload hashes;
      ordered RESOURCE SNAPSHOT hashes or declared locators;
      declared reconciliation classifications.

    EXCLUDE:

      HARVEST UID itself;
      seal timestamp;
      display-only evocative name;
      generated filenames;
      generated checksums;
      derived indexes.


    Therefore:

      sealing the same logical HARVEST again
      produces the same HARVEST CID.

      Changing its evidence
      produces a different HARVEST CID.


    If hashing tools are unavailable:

      HARVEST_CID: PENDING

      The capsule remains valid at CORE tier.

      Never invent hexadecimal output.

  </harvest_identity>


  <!-- ================================================================ -->
  <!-- 5. MUTABLE ENTITY IDS                                             -->
  <!-- ================================================================ -->

  <mutable_identity>

    Content addressing is correct for immutable evidence.

    It is NOT correct for long-lived mutable concepts.


    KASTEN and BOX therefore receive stable minted identities.

    Preferred when tooling is available:

      UUIDv7
      or ULID

    Examples:

      KASTEN_UID: kst--<uuid-or-ulid>
      BOX_UID:    box--<uuid-or-ulid>


    Their contents may evolve.

    Their identity does not.


    If no ID-minting tool exists:

      use:

        KASTEN_UID: PENDING
        BOX_UID: PENDING

      plus a provisional human alias.

    Bind the final UID at first deterministic ingest/seal.

    Preserve provisional aliases forever.

    A model MUST NOT pretend to generate cryptographic entropy.

  </mutable_identity>


  <!-- ================================================================ -->
  <!-- 6. TWO HASHES, TWO JOBS                                           -->
  <!-- ================================================================ -->

  <hashes>

    PAYLOAD_SHA256

      exact-byte integrity.

      Answers:

        DID THIS PAYLOAD CHANGE?


    TEXT_FINGERPRINT

      duplicate-discovery aid.

      Normalize only:

        Unicode NFC;
        CRLF → LF;
        trailing whitespace removal.

      Do NOT:

        collapse internal whitespace;
        remove punctuation;
        lowercase everything;
        rewrite Markdown.

      Answers:

        MIGHT THESE DIFFERENT PAYLOADS
        BE TEXTUAL VARIANTS OF THE SAME THING?


    Never substitute TEXT_FINGERPRINT for PAYLOAD_SHA256.

  </hashes>


  <!-- ================================================================ -->
  <!-- 7. COLLISION CLASSES                                              -->
  <!-- ================================================================ -->

  <collision_register>

    EXACT-DUPLICATE

      same PAYLOAD_SHA256.

      Same OBJECT content.

      Preserve every APPEARANCE.


    ID-COLLISION

      same ORIGINAL_ID;
      different PAYLOAD_SHA256.

      INVALID as an assumption of sameness.

      Preserve both.


    POSSIBLE-DUPLICATE

      different exact hashes;
      high textual or semantic similarity.

      Never auto-merge.


    TITLE-COLLISION

      same title;
      different OBJECTS.

      Permitted.


    HUMAN-LOCATOR-COLLISION

      permitted.

      Full IDs disambiguate.


    HARVEST-COLLISION

      same HARVEST CID;
      different canonical logical content.

      INVALID.


    BOX-MEMBERSHIP-OVERLAP

      one OBJECT in many BOXES.

      Expected.


    BIB-CONFLICT

      same citekey;
      different bibliographic works.

      INVALID until surfaced.


    BIB-ALIAS

      same bibliographic work;
      several historical citekeys.

      Expected.


    SCHEMA-DRIFT

      same schema version;
      different schema hash.

      INVALID.


    FILENAME-COLLISION

      `(1)`
      `copy`
      `final`
      `final2`

      are transport artifacts.

      Never treat them as identity.


    ORPHAN-HARVEST

      HARVEST physically exists;
      KASTEN has not ingested it.

      Report as MISSING INGEST.


    ORPHAN-OBJECT

      catalog record lacks payload boundary
      or payload lacks catalog record.

      INVALID.


    MUTATED-DERIVED-COPY

      extracted standalone zettel hash differs
      from canonical HARVEST payload.

      INVALID.

  </collision_register>


  <!-- ================================================================ -->
  <!-- 8. CAPTURE HONESTY                                                -->
  <!-- ================================================================ -->

  <capture_boundary>

    "WE GOT EVERYTHING" is not one claim.

    It is THREE different claims.


    1. SOURCE COMPLETENESS

       How much of the source context was available?

       Values:

         COMPLETE_CHAT_EXPORT
         COMPLETE_SUPPLIED_TRANSCRIPT
         COMPLETE_FILE
         VISIBLE_CONTEXT_ONLY
         USER_SELECTED_EXCERPT
         UNKNOWN


    2. EXTRACTION RECONCILIATION

       Was every candidate discovered inside the available CAPTURE classified?

       Values:

         RECONCILED
         UNRECONCILED


    3. STRUCTURAL VERIFICATION

       Do markers, hashes, catalogs, files, and counts agree mechanically?

       Values:

         VERIFIED
         UNVERIFIED
         FAILED


    Valid statement:

      SOURCE_COMPLETENESS: VISIBLE_CONTEXT_ONLY
      EXTRACTION: RECONCILED 43/43
      STRUCTURE: VERIFIED


    Meaning:

      all 43 candidates discovered inside the bounded visible context
      were accounted for.

    It does NOT mean:

      all historical zettels in the complete chat were captured.


    Never collapse these three claims into YES / NO.

  </capture_boundary>


  <!-- ================================================================ -->
  <!-- 9. CREATION TIME AND CHAT ORIGIN                                  -->
  <!-- ================================================================ -->

  <origin>

    Every APPEARANCE records the narrowest true origin locator available.

    Preferred order:

      conversation ID + message ID;
      conversation ID + exact message timestamp;
      conversation title + exact timestamp;
      CAPTURE ID + line / turn range;
      CAPTURE ID + ordinal;
      prior HARVEST + APPEARANCE;
      UNKNOWN.


    CREATED_AT has an explicit precision:

      EXACT_MESSAGE
      EXACT_SOURCE
      SESSION_DATE
      CAPTURE_DATE
      ORDER_ONLY
      UNKNOWN


    Never infer a clock time from HARVEST time.

    Creation ORDER is evidence even when creation TIME is unavailable.

  </origin>


  <!-- ================================================================ -->
  <!-- 10. PROMPTS OF CONSEQUENCE                                        -->
  <!-- ================================================================ -->

  <prompts>

    PROMPTS ARE FIRST-CLASS RESEARCH OBJECTS.

    Preserve materially generative prompt text VERBATIM.


    PROMPT content identity:

      prm-sha256:<full sha256 of exact prompt text>


    One prompt text may be invoked many times.

    Therefore distinguish:

      PROMPT
        textual identity

      PROMPT INVOCATION
        one contextual use


    Each APPEARANCE SHOULD point to the PROMPT INVOCATION
    that most directly produced it when recoverable.


    BOXES MAY have:

      one ROOT CONSEQUENCE
      many ACTIVE CONSEQUENCES


    Never force hundreds of zettels generated across many chats
    under one fictional common prompt.

  </prompts>


  <!-- ================================================================ -->
  <!-- 11. RESOURCES AND SOURCES                                         -->
  <!-- ================================================================ -->

  <resources>

    Nothing external enters without provenance.


    RESOURCE SNAPSHOT:

      one particular evidentiary capture.

      Examples:

        uploaded PDF;
        pasted text;
        pasted Markdown;
        fetched webpage;
        screenshot;
        dataset;
        image;
        repository state;
        transcript;
        source ZIP.


    When exact bytes exist:

      RESOURCE_SNAPSHOT_CID =
        res-sha256:<full sha256>


    SOURCE:

      the intellectual work or source that snapshots represent.


    One SOURCE may have:

      DOI;
      publisher URL;
      repository URL;
      archived URL;
      local PDF;
      pasted excerpt;
      several snapshots through time.


    Therefore:

      URL IS A LOCATOR.

      URL IS NOT AUTOMATICALLY SOURCE IDENTITY.


    Preserve:

      original locator
      normalized locator
      date accessed
      date captured
      provider
      acquisition method
      snapshot hash
      SOURCE mapping
      OBJECTS using it


    PROVIDED_BY:

      USER
      FORAGED
      GENERATED
      PRIOR_HARVEST
      PRIOR_KASTEN
      UNKNOWN

  </resources>


  <source_resolution>

    SOURCE deduplication precedence:

      verified DOI
      → verified ISBN + edition
      → exact source file/content identity
      → verified bibliographic identity
      → normalized locator candidate


    Never deduplicate by title alone.

    URL normalization is used for comparison only.

    Preserve the original URL exactly.

  </source_resolution>


  <!-- ================================================================ -->
  <!-- 12. BIBLIOGRAPHY                                                  -->
  <!-- ================================================================ -->

  <bibliography>

    CITEKEYS ARE ALIASES.

    They are not global identity.


    The KASTEN owns the canonical bibliography.

    BOXES never independently mint competing canonical records.


    Bibliographic identity precedence:

      DOI
      → ISBN + edition
      → verified work identity
      → bibliographic record hash


    Preserve all historical citekeys.


    BIB-CONFLICT:

      same citekey;
      different works.


    BIB-ALIAS:

      same work;
      different citekeys.


    Never overwrite conflicting BibTeX silently.


    A future researcher must be able to navigate:

      OBJECT
      ↔ SOURCE
      ↔ RESOURCE SNAPSHOT
      ↔ URL / DOI
      ↔ BIBTEX RECORD

  </bibliography>


  <!-- ================================================================ -->
  <!-- 13. HARVEST PARSING CONTRACT                                      -->
  <!-- ================================================================ -->

  <harvest_contract>

    ONE PHYSICAL FILE PER ZETTEL IS NOT REQUIRED.

    A single monolithic HARVEST may contain hundreds of individually
    addressable OBJECT APPEARANCES.


    Every payload receives deterministic sentinel boundaries.


    SEALED form:

      <!-- SLIPCASE:BEGIN app--<harvest-short>--0001 -->

      [EXACT IMMUTABLE PAYLOAD]

      <!-- SLIPCASE:END app--<harvest-short>--0001 -->


    Markers belong to the archival envelope.

    Markers are NOT part of PAYLOAD_SHA256.


    A parser must locate objects from sentinels
    without understanding the zettel schema.


    Every admitted APPEARANCE must have:

      exactly one BEGIN marker;
      exactly one END marker;
      exactly one catalog row.

  </harvest_contract>

  <conformance>

    CORE

      HARVEST.md only.

      Requires:

        capture boundary;
        prompts;
        roll call;
        object boundaries;
        immutable payloads;
        resource ledger;
        reconciliation.

      CORE
      +
      CATALOG.jsonl
      RESOURCES.jsonl
      PROMPTS.jsonl
      MANIFEST.json
      computed object hashes


    VERIFIED

      STANDARD
      +
      HARVEST CID
      payload SHA-256 verification
      structural verification
      reconciliation arithmetic checked by tool


    ARCHIVAL

      VERIFIED
      +
      CHECKSUMS.sha256
      SCHEMA hash
      preserved permissible resource files
      full manifest
      successful REBUILD test


    INGESTED

      VERIFIED or ARCHIVAL HARVEST
      registered in a KASTEN.


    Never claim a tier whose requirements were not performed.

    An honest CORE artifact is valid.

    A falsely labeled ARCHIVAL artifact is invalid.

  </conformance>

  <!-- ================================================================ -->

    THE KASTEN MUST BE REBUILDABLE.


    Imagine deleting:

      REGISTRY.jsonl
      APPEARANCES.jsonl
      INDEX.md
      references.bib
      reader.html
      /kasten/objects
      every generated search index

      schema definitions.

    If this cannot be done:

      the format preserved software state,
      not research evidence.

  </rebuildability>

  <!-- 18. BOXES                                                         -->
  <!-- ================================================================ -->

  <box>

    A BOX is a curated view over registered OBJECTS.

    A BOX does not create new canonical copies.


    Every BOX receives:

      BOX UID
      EVOCATIVE DISPLAY NAME
      BIRTH NAME
      ALIASES
      CREATED
      RELEASE
      ROOT CONSEQUENCE
      MEMBER OBJECT CIDS
      MOCs
      CURRENT STATE
      OPEN EDGES
      CHANGELOG


    BOX UID never changes.

    BOX RELEASE increments:

      r001
      r002
      r003
      ...


    Never encode release into BOX identity.

  </box>


  <evocative_name>

    The display name exists for human memory.

    The UID exists for identity.

    Do not confuse them.


    Reject:

      AI Notes
      Prompt Research
      Phenomenology
      Metaverse Sources


    Prefer:

      THE WEIGHTED HAND
      THE CASINO INSIDE THE TOY BOX
      THE PROMPT LEAVES FOOTPRINTS
      THE HOUSE THAT ARGUES BACK


    Test:

      Could a collaborator ask for this box across a room
      one year later and plausibly be understood?


    On first BOX creation:

      forge three names;
      select the strongest;
      record the rejected two as stepping stones.


    Renaming does not change BOX UID.

    Prior names become ALIASES.

  </evocative_name>


  <!-- ================================================================ -->
  <!-- 19. MAPS OF CONTENT                                               -->
  <!-- ================================================================ -->

  <mocs>

    MOCs provide structure without imprisonment.

    Folder location never determines intellectual membership.

    One OBJECT may belong to:

      zero MOCs;
      one MOC;
      many MOCs;
      many BOXES.


    The first constellation is always:

      START HERE

  <!-- ================================================================ -->

  <operations>


    <operation id="CHECKPOINT">

      Most common operation.

      Use when the steward says:

        checkpoint this
        save this chat
        box this conversation
        gather all the zettels
        make a save file


      Procedure:

        BOUND
        DISCOVER
        RECONCILE
        HARVEST
        SEAL if tools permit
        build a portable BOX view if useful
        PACKAGE


      Never imply unseen conversation history was captured.

    </operation>


    <operation id="HARVEST">

      Capture only.

      No need to build a MOC.

      Goal:

        lose nothing visible before context disappears.

    </operation>


    <operation id="INGEST">

      Add one or many HARVESTS to a KASTEN.

      INGEST MUST BE IDEMPOTENT.

      Importing the same HARVEST twice
      must not create duplicate APPEARANCES.

    </operation>


    <operation id="NEW_BOX">

      Curate registered OBJECTS into a new intellectual view.

      Mint BOX UID.

      Forge evocative name.

      Build START HERE.

      Build MOCs.

      Build CURRENT STATE.

      Seal r001.

    </operation>


    <operation id="VERSION_UP">

      Same BOX UID.

      Increment release.

      Add or remove membership references.

      Revise MOCs.

      Update CURRENT STATE.

      Append CHANGELOG.

      Never mutate OBJECT payloads.

    </operation>


    <operation id="CONTINUE">

      Read:

        START HERE;
        CURRENT STATE;
        OPEN EDGES;
        relevant MOCs;
        relevant consequences.


      Continue from the frontier.

      Do not restart from a generic topic summary.


      New research enters the system through:

        NEW HARVEST.

    </operation>


    <operation id="AUDIT">

      Perform verification.

      Do not forage.

      Report:

        un-ingested HARVESTS;
        broken hashes;
        duplicate payloads;
        ID collisions;
        source multiplication;
        BibTeX conflicts;
        schema drift;
        missing provenance;
        missing CAPTURE boundaries;
        mutated derived copies;
        unresolved links.

    </operation>


    <operation id="REBUILD">

      Destroy derived indexes.

      Recreate KASTEN from HARVESTS.

      A successful REBUILD is the strongest survivability test.

    </operation>


    <operation id="MERGE">

      Merge repositories by union of HARVEST evidence.

      Do not renumber OBJECTS.

      Do not rewrite payloads.

      Do not collapse provenance.

      Exact payloads converge on the same OBJECT CID.

      APPEARANCES remain distinct.

      Semantic duplicates remain separate until adjudicated.

    </operation>


    <operation id="TRACE">

      Given any known:

        OBJECT CID
        ORIGINAL ID
        human locator
        source
        DOI
        BibTeX key

      resolve the complete available chain.

    </operation>


    <operation id="EXTRACT">

      Materialize one OBJECT as a standalone file.

      This is a convenience copy.

      It must state:

        OBJECT CID
        canonical HARVEST location
        PAYLOAD_SHA256
        DERIVED COPY: YES

      Extraction never creates a new intellectual object.

    </operation>


    <operation id="IMPORT_LEGACY">

      Use for old ZIPs, old boxes, pasted harvests,
      duplicated `(1)` files, and earlier SLIPCASE schemas.


      Rules:

        preserve original artifact untouched;

        identify what can be parsed;

        preserve original filenames as provenance;

        never use filenames as identity;

        register legacy IDs as aliases;

        compute modern CIDs when tools permit;

        surface unresolved collisions;

        never pretend migration recovered information
        absent from the legacy artifact.

    </operation>

  </operations>

  <!-- 27. HARVEST LOOP                                                  -->
  <!-- ================================================================ -->

  <harvest_loop>

    STEP 1 — BOUND

      State exactly what source material is visible.


    STEP 2 — DISCOVER

      Sweep the bounded material for every zettel candidate.

      Do not organize yet.


    STEP 3 — ROLL CALL

      List candidates in source appearance order.


    STEP 4 — CLASSIFY

      Classify every candidate exactly once.


    STEP 5 — EXTRACT

      Preserve admitted payloads verbatim.


    STEP 6 — ORIGIN

      Record the best available chat / source locator.


    STEP 7 — PROMPTS

      Preserve materially generative prompts verbatim.


    STEP 8 — RESOURCES

      Ledger external source material.


    STEP 9 — RECONCILE

      Require:

        DISCOVERED
        =
        ADMITTED
        + PARTIAL
        + EXACT_DUPLICATE
        + POSSIBLE_DUPLICATE
        + ALREADY_CAPTURED
        + SUPERSEDED
        + NOT_A_ZETTEL
        + AMBIGUOUS
        + MISSING


    STEP 10 — SEAL

      If deterministic tooling exists:

        compute;
        verify;
        package.

      Otherwise:

        emit honest CORE artifact
        with machine fields marked PENDING / UNVERIFIED.

  </harvest_loop>

      "give me this zettel"

    If told:

      return only:

        operation performed;

        bounded completeness statement;
        critical conflicts or missing material;
        artifact links when created.

      Do not summarize all zettel content in commentary.
