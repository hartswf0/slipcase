    Optimize for many chats, many schemas, and thousands of zettels.

    Lossless zettelkasten compiler.

    Compile the native graph.

<lineage>
  TUFTE
    Every visible character carries evidence.
    No folder, wrapper, identifier, statistic, or ornament without a job.
    Counts are computed or marked PENDING.

  NELSON
    Links are visible, durable, and two-way.
    Address by identity, not location.
    Copying never erases origin.

  LUHMANN
    One idea, one card.
    Stable identity is separate from physical order.
    Cross-links and surprising neighbors are productive.

  GENEALOGY
    A related card is not necessarily a parent.
    A parent is the research object from which a child was actually generated,
    transformed, foraged, revised, opposed, or otherwise descended.
    Preserve that descent separately from ordinary conceptual links.
</lineage>


<laws>

  1. ONE IDEA, ONE CARD.
     One root-level .txt file per unique admitted zettel.

  2. THE ROOT IS THE DESK.
     Cards are visible before machinery.
     Never require folder → folder → ZETTEL.md.

  3. THE CARD IS THE PAYLOAD.
     Exact payload first and complete.
     Never replace it with metadata, summary, pointer, or wrapper.

  4. PAYLOAD IS IMMUTABLE.
     Corrections, extensions, disagreements, and descendants become new cards.

  5. FILENAMES CARRY HUMAN MEANING.
     Use:
       order · name · source · original ID · origin.
     Hashes belong in machine metadata.

  6. ORIGINAL IDS SURVIVE.
     They may collide.
     Never merge by ID alone.

  7. IDENTITY IS NOT LOCATION.
     Rename, move, or renumber without changing the zettel.

  8. EVERY DECLARED RELATION BECOMES GRAPH STRUCTURE.
     Preserve it in the payload and compile it operationally.

  9. EVERY [[ADDRESS]] IS AN ADDRESS.
     Resolve it or preserve it as:
       GHOST
       AMBIGUOUS
       EXTERNAL
       BROKEN EXPLICIT ID.

  10. PLATFORM, CONCEPT, AND ZETTEL ARE DISTINCT OBJECTS.
      Identical labels do not automatically collapse them.

  11. LINEAGE IS DISTINCT FROM LINKS.
      LINKS_TO means conceptual relation.
      PARENT_OF / CHILD_OF means descent.
      Never infer parenthood merely because A links to B.

  12. MULTIPLE PARENTS ARE VALID.
      A child may descend from several zettels.
      Preserve all supported parents.

  13. LINEAGE REQUIRES EVIDENCE.
      Record how a parent/kid relation was established.
      If evidence is insufficient, preserve PARENT_CANDIDATE rather than guess.

  14. NATIVE AND CURATED STRUCTURES ARE DIFFERENT.
      Native:
        PLATFORM
        LINKS
        lineage
        derived backlinks.
      Curated:
        MOCs
        arrangements.
      Curated structure may supplement but never rewrite native structure.

  15. EVERY SOURCE IS LEGIBLE.
      Never leave a naked citekey without a readable citation nearby.

  16. EVERY RESOURCE IS REGISTERED WHEN KNOWN.

  17. MISSING STAYS VISIBLE.
      Never invent provenance, citation data, lineage, dates, hashes,
      counts, authors, graph targets, or source bodies.

  18. NEVER CLAIM MORE COVERAGE THAN WAS AVAILABLE.

  19. COMPUTED FACTS ARE COMPUTED.
      Otherwise mark PENDING or UNVERIFIED.

  20. OPTIONAL INTERFACES MAY DISAPPEAR.
      Cards, provenance, graph, and lineage must remain recoverable
      without the reader.
</laws>

<genealogy>

  LINEAGE answers:

    WHICH ZETTEL DID THIS COME FROM?
    WHICH ZETTELS CAME FROM THIS?
    HOW MANY GENERATIONS DEEP IS THIS BRANCH?
    WHERE DID THE BRANCH SPLIT OR RECOMBINE?


  PARENT_OF is created only from supported descent evidence.

  Evidence priority:

    1. explicit payload field:
         PARENT
         PARENTS
         CHILD OF
         DERIVED FROM
         FORAGED FROM
         or equivalent unambiguous lineage declaration

    2. explicit session/checkpoint provenance stating:
         this zettel was generated as a child of <ID>

    3. explicit generating prompt/input pair demonstrating:
         parent zettel supplied as the research object
         → resulting child zettel

    4. consistent internal evidence such as:
         CITATION TRAIL beginning with earlier zettel ID
         AND that ID appearing in LINKS
         AND available context identifies the operation as recursive descent

       Record this as:
         CONTEXT_SUPPORTED

    5. suggestive but incomplete evidence:
         PARENT_CANDIDATE

  NEVER:

    treat every LINKS target as a parent;
    treat shared PLATFORM as parenthood;
    infer parenthood from topical similarity;
    infer parenthood from filename order alone.


  LINEAGE EVIDENCE STATES:

    EXPLICIT_FIELD
    EXPLICIT_CONTEXT
    PROMPT_INPUT_OUTPUT
    CONTEXT_SUPPORTED
    CANDIDATE
    UNKNOWN


  MULTI-PARENT CHILDREN:

    preserve every supported parent.

    Example:

      A ─┐
         ├──→ C
      B ─┘


  DERIVED GENEALOGY:

    CHILD_OF
      inverse of PARENT_OF

    KIDS
      direct children only

    ANCESTORS
      transitive parents

    DESCENDANTS
      transitive children

    GENERATION
      shortest depth from known lineage root when acyclic

    ROOT
      no known parent in bounded material

    LEAF
      no known child in bounded material

    BRANCH POINT
      parent with >1 direct child

    MERGE CHILD
      child with >1 direct parent


  CYCLES:

    parent lineage should normally be acyclic.

    If a cycle appears:
      preserve it;
      flag LINEAGE_CYCLE;
      do not invent a correction;
      generation depth becomes UNRESOLVED for the affected component.
</genealogy>

<adaptability>

  FOREIGN SCHEMA
    Do not require a fixed zettel field set.
    Preserve cards verbatim.
    Recognize useful labels and [[addresses]] without rewriting them.

  THIN CARDS
    No source, ID, platform, links, or parents is allowed.
    Preserve:
      SOURCEUNKNOWN
      NOID
      zero edges
      zero known parents.

  MIXED INPUT
    Accept chat, paste, files, prior checkpoints, JSON, and overlap.

  NO TOOLS
    Emit the deck as text using intended filenames.
    Mark computed material PENDING / UNVERIFIED.

  PARTIAL CONTEXT
    Capture only visible material and declare the boundary.

  LINEAGE WITHOUT EVIDENCE
    Do not turn conceptual similarity into genealogy.
    Use PARENT_CANDIDATE only when evidence exists but is incomplete.

  SCALE
    Tens:
      show whole field.

    Hundreds:
      neighborhood-first graph and lineage.

    Thousands:
      search-first;
      platform and branch views;
      lazy detail.

  MERGE
    Merge exact payload identity only.
    Preserve all appearances, ghosts, graph relations,
    parent/kid relations, candidates, and collisions.

    Then rerun:
      relation resolution
      ghost resolution
      lineage resolution
      generation depth
      roots/leaves
      bibliography
      reader/map generation.

  UNLISTED CASE
    Decide by the laws.
    Prefer preserving two objects over collapsing them.
    Prefer visible uncertainty over confident invention.
    Record the decision.

  CONFLICT ORDER

    no lost cards
      → exact payloads
      → cards visible
      → source / ID / origin
      → native graph
      → genealogy
      → ghosts
      → readable index/map/lineage
      → sources
      → computable data
      → reader
      → machinery out of the way.
</adaptability>
